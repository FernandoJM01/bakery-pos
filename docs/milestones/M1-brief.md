This milestone delivers the skeleton every later milestone builds on: the repository layout, CI, three environments, and secure access. Staff log in by PIN on enrolled tills, roles and permissions are enforced on both sides, and the owner manages branches, staff and devices from the back office. No selling yet.

## 3. Conventions (all milestones)

- **IDs:** UUID v7, generated by whoever creates the record (the till for till-created records). Never sequential integers in the API.
- **Time:** stored and sent as UTC ISO 8601; displayed in `America/Mexico_City` unless the branch sets another zone.
- **Money:** integer centavos (`int`), field names end in `Cents`. No floats anywhere. (Not used until M2.)
- **JSON:** camelCase fields. Errors use the `Error` schema in the contract: `{ code, message, details? }` with stable `code` strings (`AUTH_INVALID_PIN`, `AUTH_LOCKED`, `PERMISSION_DENIED`, …).
- **API version:** every route is under `/v1`.
- **Language:** code, comments, commits and API in English. All user-facing text in Spanish (Mexico) through the l10n files (`app/lib/l10n/app_es.arb`); no literal strings in widgets.
- **Secrets:** only from environment variables; the server refuses to start if `JWT_SECRET`, `DATABASE_URL` or `DEVICE_TOKEN_PEPPER` is missing. No defaults in code.
- **Logging:** structured JSON logs; never log PINs, passwords, tokens or full device secrets.

## 4. Data model for M1 (Dev A)

| Table | Key columns | Notes |
| --- | --- | --- |
| `branch` | id, code (unique, e.g. `SUC1`), name, address, timezone, is_active, created_at, updated_at | |
| `staff` | id, full_name, display_name, role, email (nullable, unique), password_hash (nullable), pin_hash, offline_pin_verifier, pin_updated_at, is_active, failed_pin_attempts, locked_until, created_at, updated_at | `role` enum: `OWNER`, `BRANCH_MANAGER`, `CASHIER`, `BAKER`. Owner needs email + password for the back office. |
| `staff_branch` | staff_id, branch_id | Which branches a staff member works in. Owner is implicitly all branches. |
| `permission` | key (PK), description | Seeded from the matrix in section 6. |
| `role_permission` | role, permission_key | Seeded; not editable in Phase 1. |
| `device` | id, branch_id, name, type (`TILL`, `PRODUCTION`), status (`PENDING`, `ACTIVE`, `REVOKED`), enrollment_code_hash, enrollment_expires_at, token_hash, last_seen_at, app_version, created_by, created_at, revoked_at | |
| `auth_session` | id, staff_id, device_id (nullable for back office), refresh_token_hash, expires_at, revoked_at, created_at | |
| `audit_log` | id, occurred_at, branch_id, device_id, actor_staff_id, approver_staff_id, action, entity_type, entity_id, data (jsonb) | Insert-only: revoke UPDATE and DELETE from the app's database role. |

Hashing:
- PIN and password: **argon2id** (memory 64 MiB, iterations 3, parallelism 1), per-record salt (built into the encoded hash).
- Offline PIN verifier: a second, independent argon2id hash of the PIN with its own salt, computed when the PIN is set. Only this one is ever sent to tills.
- Device token and refresh token: random 32 bytes, stored as SHA-256 with a server pepper (`DEVICE_TOKEN_PEPPER`). Raw values are shown once.
- Enrollment code: 8 characters from an unambiguous alphabet (no 0/O/1/I), valid 30 minutes, single use.

Seed (dev and staging only, never production): 2 branches (`SUC1`, `SUC2`), one owner, one manager, two cashiers and one baker per branch, with random PINs printed once in the seed output. Production gets only the owner, created by a one-off CLI command `npm run create-owner`.

## 5. Behaviour

### 5.1 Device enrollment
1. The owner creates a device in the back office (branch, name, type). The server returns a one-time enrollment code.
2. On first start, the till shows the enrollment screen; the person types the server URL (prefilled per build) and the code.
3. `POST /v1/devices/activate` returns the device and `deviceToken`. The till stores them in secure storage (Android Keystore through `flutter_secure_storage`).
4. Every till request sends `X-Device-Token`. Revoked or unknown devices get `401 DEVICE_REVOKED` / `DEVICE_UNKNOWN`, and the till returns to the enrollment screen and wipes its local data.

### 5.2 Staff login on the till
- The login screen lists the active staff of the device's branch as photo/initial tiles. The staff list comes from `GET /v1/devices/me/staff`.
- PIN length 4 to 6 digits. The keypad has an explicit confirm key (PIN length is not leaked by auto-submit).
- **Online:** `POST /v1/auth/pin-login` with `X-Device-Token` → access token (15 min) + refresh token (until 04:00 local next day). The till refreshes silently.
- **Offline:** the staff bundle includes each staff member's `offlinePinVerifier`. The till verifies locally, issues a local offline session, and marks every action taken in it `offline: true`. When the device is back online the till must call `pin-login` again before the next sync.
- **Lockout:** 5 wrong PINs for one staff member → locked 5 minutes, on the server and on the till independently. The 6th attempt during lockout returns `423 AUTH_LOCKED` with `lockedUntil`.
- **Auto-lock:** after 2 minutes without touches the till returns to the login screen; the current user's screen state is kept for 30 minutes and restored if the same person logs back in.
- **Switch user:** a tap on the user's name in the top bar goes to login without logging out other held state.

### 5.3 Back office login
- Owner (and managers who have an email) log in with email and password in the browser. Same token model, no device token.
- 10 wrong passwords in 15 minutes → locked 15 minutes.

### 5.4 Manager approval
- Any screen can ask for approval with `POST /v1/auth/approvals` (approver staff ID, PIN, action key, optional reference). The server checks the PIN and that the approver holds the permission for that action, and returns a single-use `approvalToken` valid 2 minutes.
- Offline, the till verifies the manager's PIN with the offline verifier and records the approval locally; it syncs later as an audit entry.
- Every approval writes an `audit_log` row with both actor and approver.

### 5.5 Permissions
- `GET /v1/me` returns the staff member, their branches and their permission keys. The app shows or hides navigation from this list; **the server checks every endpoint independently**.
- Server: one `@RequirePermission('staff.manage')` decorator per route plus a global guard that rejects any route without either a permission decorator or an explicit `@Public()`. A unit test fails the build if any controller route lacks one.

## 7. Screens (Dev B)

Till (`main_till.dart`): enrollment, staff login (tiles + keypad), lock screen, role-based shell with empty placeholder sections for the permissions the user holds, sync/online indicator in the top bar (static "online/offline" for now), manager approval dialog (reusable widget).

Back office (`main_backoffice.dart`): login, branches (list, create, edit), staff (list, create, edit, deactivate, reset PIN, assign branches), devices (list, create with enrollment code shown once, revoke), audit log (filter by date, branch, staff, action).

Use the visual language from the template in `legacy/` (dark espresso palette, amber accent, 56 dp targets) through a single theme file. The architect delivers wireframes for the four key flows (sale, shift close, standing-order pickup, oven intake) during M1; they are not built in M1.

## 8. CI (both)

`.github/workflows/ci.yml`, on every PR and push to `main`:

- **server:** `npm ci`, lint (no warnings), typecheck, unit tests, e2e tests against a PostgreSQL 16 service container, `npm audit --audit-level=high`, contract check (requests and responses in e2e tests are validated against `contracts/openapi.yaml`).
- **app:** `dart format` check, `flutter analyze` (no issues), unit and widget tests, build the web bundle and the Android APK.
- **contract:** `redocly lint contracts/openapi.yaml`.
- Server services and app domain code must stay at or above 80% line coverage.
